# DataBridge requirements and design spec

Status: draft for candidate review  
Date: 2026-09-24  
Input: [intent.md](intent.md) and the authoritative [take-home brief](instructions/README.md)

## Scope and priorities

**Submission requirements:** all Phase 1, Phase 2, and Phase 3 acceptance criteria, plus encrypted SFTP passwords at rest and large-file transfer with bounded memory and credible performance evidence. Encryption is part of the initial connection-store design, with a stable key outside the database. **Further bonuses and polish:** a healthcheck, connector contract tests, application-served OpenAPI documentation, explicit collision behavior, bounded listings, and a reviewer smoke command. **Excluded:** S3 or other cloud connectors, background workers, scheduling, format conversion, public API authentication, multi-tenant isolation, idempotency keys, and production deployment.

The brief formally requires only Phases 1 and 2; Phase 3 and encryption are additional commitments for this submission. Preserve the connector abstraction and working transfers while implementing them. Record any deliberate cut in the submission README and update this spec if the agreed scope changes.

**Implementation baseline:** Python with compatible pinned dependencies; FastAPI and Pydantic for the API, Paramiko for SFTP, standard-library `sqlite3`/CSV/JSON for storage and parsing, `cryptography` Fernet for authenticated password encryption, and pytest for tests. Keep a small `databridge` package with API, store, connector, transfer, preview, and encryption modules. The planned local start is `uvicorn databridge.api:app --host 127.0.0.1 --port 8080 --workers 1`; `databridge.api` is a new module to create. Only one service process may use the SQLite database at a time. Multi-process transfer coordination is outside scope.

**Delivery order:** establish the store/encryption and connector contract, then prove Phase 1, Phase 2 against Docker, and Phase 3 before polishing bonuses. No numeric time box has been provided. If time pressure requires reducing scope, seek a deliberate revision of this spec; first candidates are fine-grained benchmark phase timings, the automated wrapper around the documented smoke path, then the healthcheck. Keep the required phases, encrypted credentials, bounded-memory transfer, and their correctness tests unless the candidate explicitly changes the intended outcome. Start Git history before implementation, commit the reviewed intent/spec first, and make subsequent commits by working vertical slice.

## User-visible requirements

| ID | Priority | Requirement and observable acceptance |
| --- | --- | --- |
| R1 | Required | Create a uniquely named local connection with a directory path. Create the directory if it is missing; reject an existing non-directory or an uncreatable path with a useful client error. A connection remains usable after stopping and restarting the service. |
| R2 | Required | List regular files at a connection's configured root through the HTTP API. A missing connection returns 404. Limit both entries scanned and results returned; report when a result is truncated rather than silently implying completeness. |
| R3 | Required | Preview the first several rows of a CSV or JSON file through a local connection. The response names the file and returns rows in a documented shape. |
| R4 | Required | Create an SFTP connection with host, port, username, password, and a remote root directory. List files through the same connector interface used by local connections. The supplied container works with remote root `data`. |
| R5 | Required | Transfer a file local-to-SFTP and SFTP-to-local using the same transfer code. Compare source and destination bytes, including a non-text test file. The transfer code contains no connector-type branch and performs no parsing or transformation. Refuse an existing destination by default; an explicit `overwrite` request safely replaces it on both supported connectors. Reject the same stored connection name and filename as source and destination, without a connector-type check. |
| R6 | Required | Return or retrieve a transfer record with status, start time, completion time on success, and bytes copied. Failed transfers have a failure time, a safe error reason, the failure phase, and bytes written to staging before failure. The requested destination remains absent or unchanged after a handled failure. An interrupted process leaves a failed status on next startup and may leave an identifiable, unpublished staging file. |
| R7 | Required | Give clear, appropriate API errors for invalid connection settings, duplicate names, missing connections/files, bad SFTP credentials, unreachable SFTP server, and destination write failures. No raw stack trace or password appears in a response. Record a local JSON-line request event with a request ID, status, error code, and allowlisted parameters so failures can be traced without logging raw bodies. |
| R8 | Submission requirement | Infer `string`, `integer`, `float`, `boolean`, or `date` for CSV columns and JSON object fields from previewed records. The same preview service works through either connector. Document how empty and mixed values are treated. |
| R9 | Bonus | A healthcheck verifies access to a stored connection without moving file content; authentication, server availability, and configured-root permission failures yield distinguishable, actionable results without exposing secrets. |
| R10 | Submission requirement | Transfer reads and writes fixed-size byte chunks so memory use does not grow with file size. Verify a large binary transfer in both directions with matching hashes and record size, duration, throughput, peak process memory, and host/container platform; if the environment cannot support the full test, document the largest completed test and an estimate of practical limits with assumptions and uncertainty. |
| R11 | Bonus | Shared parameterized scenarios exercise list/read/write behavior for both connectors, complemented by Docker SFTP integration. Cover empty files, sizes around a transfer chunk boundary, refused and explicit-overwrite destination collisions, path escapes, and failure after at least one chunk; test symlink escapes where the backend supports creating them. Assert bytes, status, preserved destination on failure, and staging cleanup. |
| R12 | Bonus | The running service serves accurate OpenAPI documentation, and the README links to it and includes copyable main-operation examples. |
| R13 | Submission requirement | SFTP passwords are encrypted before the connection is persisted, using an externally supplied, stable key. Stored ciphertext differs from the password; the connection remains usable after restart with the same key. Passwords remain redacted from read responses and logs. Startup fails clearly if the key is absent or does not match the persisted encrypted data. |
| R14 | Polish | A documented smoke command, run after setup, exercises local and SFTP connections, preview, transfers in both directions, status, and byte or hash equality against the supplied container. |

## HTTP contract

Use JSON requests and responses. Names and paths below are proposed public routes, not routes mandated by the brief:

| Operation | Route | Result |
| --- | --- | --- |
| Create connection | `POST /connections` | 201 and redacted connection record |
| List/get connections | `GET /connections`, `GET /connections/{name}` | Redacted records |
| List files | `GET /connections/{name}/files` | File names only and a `truncated` indicator at the configured root |
| Preview file | `GET /connections/{name}/files/{filename}/head?limit=5` | Format, rows, inferred schema; 5 rows by default |
| Check connection | `POST /connections/{name}/healthcheck` | Reachable status or safe failure |
| Transfer file | `POST /transfers` | Completed record on success; error with transfer ID on failure; `overwrite` defaults to false |
| Inspect transfer | `GET /transfers/{id}` | Persisted status and metrics |

**Request and response shapes.** `POST /connections` accepts either `{"name":"local_data","type":"local","path":"./data"}` or `{"name":"remote_server","type":"sftp","host":"127.0.0.1","port":2222,"username":"testuser","password":"...","root":"data"}`. Names match `[A-Za-z][A-Za-z0-9_-]{0,63}`. A local path must name an existing directory and is stored as an absolute resolved path so restarting from another working directory does not change its meaning. SFTP creation checks field shape but does not contact the server; healthcheck and file operations test live credentials and access. Connection responses contain the name, type, and nonsecret settings; the `password` key is absent, including from list and get responses.

`POST /transfers` accepts `{"source":"local_data","source_file":"customers.csv","destination":"remote_server","destination_file":"customers.csv","overwrite":false}`. `overwrite` may be omitted and defaults to false. A transfer record contains `id`, source and destination names and filenames, `status`, `started_at`, `completed_at`, `failed_at`, `bytes_copied`, `failure_phase`, and a safe `error` message; fields that do not apply are null. List returns `{"connection":"local_data","files":["customers.csv"],"truncated":false}`. Preview returns `filename`, `format`, `rows`, and a `schema` mapping field name to inferred type. CSV row values remain strings as read; JSON row values retain their JSON types. Inference describes the preview sample and does not transform either file.

**Bounds.** File listing returns at most 1,000 names and scans at most 10,000 entries; `truncated=true` whenever a cap stops enumeration. Sort returned names for stable output. Preview defaults to 5 rows, allows 1–100 rows, and reads at most 1 MiB of source content. Exceeding the byte budget before a valid preview can be produced is an error. Transfer uses 1 MiB byte chunks. These values are implementation constants with boundary tests, not user-configurable API options.

The service does not need asynchronous jobs for this exercise. A transfer request finishes when the copy and destination finalization finish. Status transitions are `running` to `completed` or `failed`. Persist the initial record before I/O and persist the terminal state even when an expected connector error occurs. An error response includes the transfer ID so the failed record can be inspected. Timestamps use UTC ISO 8601. `bytes_copied` counts bytes successfully written to the staged destination; a nonzero value on failure does not mean the final destination was published. Count bytes rather than rows because a data-agnostic copy never parses records. Record a safe failure phase such as source connection, destination connection, copy, or finalization. With the documented one-process runtime, startup marks records left `running` as `failed` with an interruption reason; another service process must not share that database concurrently.

Errors use `{"error":{"code":"FILE_NOT_FOUND","message":"File not found","transfer_id":null}}`; `transfer_id` is set for a failed transfer request after its record is created. Use these stable codes and statuses:

| HTTP status | Codes |
| --- | --- |
| 422 | `INVALID_REQUEST` for malformed request shape or field types |
| 400 | `INVALID_CONNECTION_SETTINGS`, `INVALID_FILENAME`, `SAME_FILE`, `UNSUPPORTED_PREVIEW_FORMAT`, `MALFORMED_FILE`, `PREVIEW_LIMIT_EXCEEDED` |
| 404 | `CONNECTION_NOT_FOUND`, `FILE_NOT_FOUND`, `TRANSFER_NOT_FOUND` |
| 409 | `CONNECTION_EXISTS`, `DESTINATION_EXISTS` |
| 502 | `SFTP_AUTH_FAILED`, `SFTP_HOST_KEY_REJECTED`, `SFTP_OPERATION_FAILED` |
| 503 | `SFTP_UNAVAILABLE`, `CONNECTION_ROOT_UNAVAILABLE` |
| 500 | `LOCAL_IO_ERROR`, `SOURCE_READ_FAILED`, `DESTINATION_WRITE_FAILED`, `TRANSFER_INTERNAL_ERROR` |

Avoid raw stack traces and secrets in error messages or logs. A remote authentication failure must not be reported as failure of the API caller's authentication. Keep the error mapper in the API boundary and raise typed domain/connector errors below it. Log one JSON event per HTTP request beside the SQLite database (default `state/databridge.requests.jsonl`), with mode 0600. Include the route template, request ID, status, duration, relevant path/query parameters, and allowlisted connection or transfer fields. Never log passwords, keys, raw bodies, or arbitrary query parameters. Return the request ID in the `X-Request-ID` response header.

## Design boundaries

1. **Connection store:** SQLite holds names, types, type-specific settings, and transfer records. Encrypt the SFTP password at the persistence boundary from the first implementation. Require a stable encryption key from the environment at startup, never store it with the database, and keep both the database and key material out of Git. Persist an encrypted key-check marker so a wrong key fails at startup, including when no SFTP connection has been created. Return redacted connection views. Connection creation validates configuration shape; the healthcheck handles live connectivity.
2. **Connector contract:** A small interface defines `list`, `read`, and `write`. `read` and `write` yield context-managed binary streams, with connector-owned setup and cleanup. The local and SFTP implementations own path resolution, file opening, and destination finalization. Each active transfer owns its SFTP session and closes it on every outcome; no mutable SFTP client is shared across requests. A registry/factory selects a connector when a stored connection is opened.
3. **Transfer service:** Opens source and destination connectors, copies fixed-size byte chunks, updates the byte count, and records the outcome. It does not inspect extensions or choose logic based on connector type. A same-file precheck compares stored connection names and validated filenames; different connection aliases to the same physical file are not identified, but staging prevents the early source truncation that check is meant to avoid. Stage a write under a reserved `.{destination}.databridge-{transfer_id}.part` name in the destination root; reject this reserved pattern in user-supplied filenames and exclude it from listings. A handled write failure removes its stage so callers do not mistake a partial file for a completed transfer. After a process crash, an orphan stage may remain; the next startup marks the transfer failed, and the README gives a transfer-ID-based manual cleanup procedure. Automatic remote orphan cleanup is outside scope. An existing destination is refused by default; explicit overwrite is supported only with safe finalization on the target connector. The collision rule is checked before the copy and again at publish time, with the guarantee tested against the supplied SFTP server. If a remote server cannot finalize safely, report failure rather than success. Do not claim universal race-free behavior for untested SFTP servers.
4. **Preview service:** Reads through the connector contract and parses only supported formats. CSV uses its header; JSON expects an array of objects. Limit returned rows and bytes read; return a clear error when the preview cannot be produced within those limits. Empty/null values do not determine a type; compatible integers and floats widen to `float`, while incompatible values widen to `string`. Check booleans before numeric types and recognize ISO dates. CSV text may infer numeric or boolean types; JSON numeric and boolean strings remain strings, while native JSON numbers and booleans retain their types. Return a clear error for unsupported or malformed input. Preview parsing never affects transfer bytes.
5. **API layer:** Validates requests, creates missing configured local directories, maps domain/connector failures to stable HTTP errors, and exposes typed response models and OpenAPI examples. A request middleware writes a single redacted JSON event after each response. Blocking SFTP operations use synchronous handlers.

Restrict API file names to one file at the configured root. Reject separators, `.`/`..`, and local symlink escapes; enumerate only regular files. Bound listing by entries scanned as well as files returned, and label a partial listing as truncated; ordering of a partial listing is unspecified. This keeps the exercise's file scope clear without designing a recursive virtual filesystem. For SFTP, verify server identity against a configured known-hosts source; document how to trust the local Docker server. Set connection and I/O timeouts and close SSH/SFTP resources on every outcome.

## Verification and submission evidence

The live [requirement evidence map](verification.md) tracks R1–R14 as implementation and tests land. A planned row is not evidence of a passing requirement.

- Unit tests: deterministic schema inference, filename validation, transfer state transitions and failure cleanup, and shared connector behavior. Use a compact scenario table for both connectors rather than a separate test framework; keep connector-specific assertions where needed. Test empty files, exact/chunk-adjacent sizes, existing destinations, same-file copies, path and symlink escapes, truncated listings, and failure after a chunk has been written. Avoid tests that merely repeat the implementation.
- API tests: persistence across app restart, local-directory creation, response redaction, status/errors, redacted request events, and OpenAPI availability.
- Credential tests: inspect the stored row to confirm the password is absent in plaintext; restart with the same key and use the connection; reject an absent or wrong key at startup without disclosing secret material.
- Docker integration: follow the local trust bootstrap, prove an upload into the writable `data` directory from a fresh checkout, connect with valid and invalid credentials, list and preview via SFTP, transfer CSV and binary fixtures in both directions, and compare bytes. Exercise server-down behavior and service restart with an interrupted transfer record and reserved staging file; the record becomes failed and the staging name is absent from API listings.
- Large-file evidence: run a reproducible local-to-SFTP and SFTP-to-local benchmark at two sizes, targeting 16 MiB and 256 MiB when the environment permits. Compare SHA-256 hashes, report elapsed time, effective throughput, and peak process memory for each direction and size. Record host architecture, SFTP image architecture, Docker runtime/emulation if applicable, and disk/network conditions; these measurements describe the test environment, not a universal service limit. Where practical, separate connection, copy, and finalization timing so a slowdown can be attributed. Look for memory growth tied to file size or a disproportionate throughput drop. If a large run is unavailable, provide the largest successful measurement plus a bounded estimate based on chunk size, observed throughput, disk space, network/SFTP behavior, and synchronous request lifetime.
- Manual reviewer path: follow a fresh-checkout README exactly, including stable secret-key and known-hosts setup. After setup, run one documented smoke command against the actual Docker SFTP server, covering connection creation, preview, both transfer directions, status, and byte or hash comparison. Verify commands and examples against the final tree.
- Submission: working service; README with setup, API usage, decisions, cuts, and improvements; `ai-collaboration-summary.md` generated at the end from the brief's exact prompt and kept at or below 500 words; intentional Git commits.

## Source-specific setup notes and concerns

- The implementation layout is root-level `data/customers.csv`, `data/products.json`, and `docker-compose.yml`, with the supplied `instructions/` files retained as source material. Copy the supplied `customer.csv` under the plural target name; it has 15 customer records. Run Compose from the repository root so its relative `./sftp_data` mount resolves there.
- The root-level Compose file will add a project-scoped named volume at `/etc/ssh` so generated host keys survive normal container recreation and `docker compose down`/`up`. The local bootstrap creates `sftp_data` as the host user, starts the container, captures the key presented at `127.0.0.1:2222` into a project-scoped, gitignored known-hosts file, and verifies a write, read, rename, and delete inside remote root `data`. Capturing the presented key is an explicit trust-on-first-use step for this local Docker test server only; runtime connections still reject unrecognized host keys. Re-run trust bootstrap after `docker compose down -v`, which deletes the key volume. If a platform's bind mount denies writes, setup must stop with a targeted permission diagnostic and a fix limited to `sftp_data`; matching the container UID to the host UID is one possible fix, not a prerequisite on every platform.
- Isolated preflight on 2026-09-24: the unmodified supplied Compose file worked on this macOS/Docker Desktop host (host UID 501, container user UID 1001), including SFTP upload, download, rename, and delete; both downloads matched the original SHA-256. The initially auto-created host directory was writable through this mount, so a UID mismatch alone does not prove failure here. Without a key volume, forced recreation changed both SSH host-key fingerprints and the old known-hosts entry correctly rejected the server. With a named volume at `/etc/ssh`, host keys stayed identical across forced recreation and `down`/`up`, and the previously trusted key still permitted SFTP operations. The Docker engine reported arm64 while `atmoz/sftp:alpine-3.7` is linux/amd64, so performance measurements on this host include emulation overhead. Repeat the write preflight on the reviewer's platform; this observation is not a cross-platform guarantee.
- Encryption needs a durable key setup and a restart test. Never generate an unpersisted key at each process start. Document that losing the key makes the stored SFTP credentials unusable; key rotation is outside this exercise.
- Transfer input is assumed stable for the duration of a copy; source snapshots, resumable transfers, automatic destination re-read checksums, and repeated-request deduplication are outside this exercise. Document this limit and measure file integrity in the integration and benchmark tests.
- This is a local, trusted development API with one shared connection and transfer namespace. Multiple callers can use it, but requests carry no user or tenant identity, so every caller has the same access. Bind the example server to localhost. Encryption at rest protects the stored password; it does not restrict what an API caller can do with a connection. A shared multi-tenant service would need authenticated tenant identity, tenant-scoped queries and authorization on every resource, isolated file roots and secrets, network access controls for user-supplied SFTP hosts, and tests that cross-tenant access is denied. One service instance per tenant is a simpler alternative if isolation is later required.
