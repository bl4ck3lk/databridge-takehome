# DataBridge requirements and design spec

Status: implemented and verified; revised after the 2026-09-25 reviews (see `docs/ai-work-log.md`)
Date: 2026-09-24  
Input: [intent.md](intent.md) and the authoritative [take-home brief](instructions/README.md)

## Scope and priorities

**Submission requirements:** all Phase 1, Phase 2, and Phase 3 acceptance criteria, plus encrypted SFTP passwords at rest and large-file transfer with bounded memory and credible performance evidence. Encryption is part of the initial connection-store design, with a stable key outside the database. **Further bonuses and polish:** a healthcheck, connector contract tests, application-served OpenAPI documentation, explicit collision behavior, bounded listings, and a reviewer smoke command. **Excluded:** S3 or other cloud connectors, background workers, scheduling, format conversion, public API authentication, multi-tenant isolation, idempotency keys, and production deployment.

The brief formally requires only Phases 1 and 2; Phase 3 and encryption are additional commitments for this submission. Preserve the connector abstraction and working transfers while implementing them. Record any deliberate cut in the submission README and update this spec if the agreed scope changes.

**Implementation baseline:** Python with compatible pinned dependencies; FastAPI and Pydantic for the API, Paramiko for SFTP, standard-library `sqlite3`/CSV/JSON for storage and parsing, `cryptography` Fernet for authenticated password encryption, and pytest for tests. The small `databridge` package contains the API, store, connectors, transfer, and preview modules; encryption belongs to the store boundary. `make run` starts `python -m databridge serve`. Its optional `--port` accepts only 1–65535, and the command checks it before it reads a setting. The command then reads every setting, takes the database lock, verifies the database, and opens the request log. Only after these steps does Uvicorn listen on 127.0.0.1:8080, in the same process. A setting or database problem is a `StartupError`. The command then prints one line that names every problem and exits with status 1. It shows no traceback and binds no port. Any other startup exception is a defect and keeps its traceback. The ASGI lifespan does not do these steps, because Starlette reports any lifespan failure with a formatted traceback. `make logs` follows the file that `python -m databridge request-log-path` prints; that command reports a settings problem in the same one-line form. Only one service process may use the SQLite database at a time: an exclusive lock file beside the database (`<database>.owner.lock`) enforces this, and a second process fails at startup before it reads or changes the database. Multi-process transfer coordination is outside scope. `DATABRIDGE_DB_PATH` and `DATABRIDGE_KNOWN_HOSTS` are required absolute paths, so the working directory never selects a different database or trust file; `make quickstart` writes them to `.env`. Startup names every missing or invalid setting in one message. Invalid settings include a key that is not a Fernet key and a `DATABRIDGE_ALLOWED_HOSTS` value that names no host. Only a missing setting also names `make quickstart`, because quickstart never replaces an existing value.

**Delivery order:** establish the store/encryption and connector contract, then prove Phase 1, Phase 2 against Docker, and Phase 3 before polishing bonuses. No numeric time box has been provided. If time pressure requires reducing scope, seek a deliberate revision of this spec; first candidates are fine-grained benchmark phase timings, the automated wrapper around the documented smoke path, then the healthcheck. Keep the required phases, encrypted credentials, bounded-memory transfer, and their correctness tests unless the candidate explicitly changes the intended outcome. Start Git history before implementation, commit the reviewed intent/spec first, and make subsequent commits by working vertical slice.

## HTTP contract

Use JSON requests and responses. Names and paths below are proposed public routes, not routes mandated by the brief:

| Operation | Route | Result |
| --- | --- | --- |
| Create connection | `POST /connections` | 201 and redacted connection record |
| List/get connections | `GET /connections`, `GET /connections/{name}` | Redacted records |
| Replace connection | `PUT /connections/{name}` | 200 and the redacted record; the body is a full connection whose `name` matches the path, including the SFTP password |
| Delete connection | `DELETE /connections/{name}` | 204; its files and transfer records stay |
| List files | `GET /connections/{name}/files` | File names only and a `truncated` indicator at the configured root |
| Preview file | `GET /connections/{name}/files/{filename}/head?limit=5` | Format, rows, inferred schema; 5 rows by default |
| Check connection | `POST /connections/{name}/healthcheck` | `reachable` plus `writable` (a probe file under the reserved prefix is created and removed), or a safe failure; a probe that cannot be removed fails the check with a message that names it (`SFTP_OPERATION_FAILED` or `SFTP_UNAVAILABLE` for SFTP, `LOCAL_IO_ERROR` for local) |
| Transfer file | `POST /transfers` | Completed record on success; error with transfer ID on failure; `overwrite` defaults to false |
| List transfers | `GET /transfers?status=running&limit=50` | Newest records first, optionally one status; `limit` is 1–500 |
| Inspect transfer | `GET /transfers/{id}` | Persisted status and metrics |

**Request and response shapes.** `POST /connections` accepts either `{"name":"local_data","type":"local","path":"./data"}` or `{"name":"remote_server","type":"sftp","host":"127.0.0.1","port":2222,"username":"testuser","password":"...","root":"data"}`. Names match `[A-Za-z][A-Za-z0-9_-]{0,63}`. Unknown fields are rejected in connection and transfer requests, a body that cannot be decoded as JSON is `INVALID_REQUEST`, an SFTP password must be valid Unicode text, an IPv6 zone may use only ASCII letters, digits, `.`, `_`, and `-`, and the brief's SFTP `user` field is accepted for `username`; `root` is required. A host is an IP address or an ASCII DNS name (punycode for internationalized names) and is stored in lower case, as OpenSSH records hosts in known_hosts. A path, root, or username is at most 4096 characters and contains no control characters, so none can forge a log line. Field problems are `INVALID_REQUEST` with details. A local path names a directory, which is created if missing, then stored as an absolute resolved path so restarting from another working directory does not change its meaning. SFTP creation checks field shape but does not contact the server; healthcheck and file operations test live credentials and access. Connection responses contain the name, type, and nonsecret settings; the `password` key is absent, including from list and get responses.

`POST /transfers` accepts `{"source":"local_data","source_file":"customers.csv","destination":"remote_server","destination_file":"customers.csv","overwrite":false}`. `overwrite` may be omitted and defaults to false. A transfer record contains `id`, source and destination names and filenames, `overwrite`, `status`, `started_at`, `updated_at`, `completed_at`, `failed_at`, `bytes_copied`, `failure_phase`, `error_code`, and a safe `error` message; fields that do not apply are null, and the published OpenAPI example shows them as null. List returns `{"connection":"local_data","files":["customers.csv"],"truncated":false}`. Preview returns `filename`, `format`, `rows`, and a `schema` mapping field name to inferred type. CSV row values remain strings as read; JSON row values retain their JSON types. Inference describes the preview sample and does not transform either file.

**Bounds.** File listing returns at most 1,000 names and scans at most 10,000 entries; `truncated=true` whenever a cap stops enumeration. Sort returned names for stable output. Preview defaults to 5 rows, allows 1–100 rows, parses at most 1 MiB of source content, and reads one extra byte to detect truncation. Exceeding the byte budget before a valid preview can be produced is an error. Transfer uses 1 MiB byte chunks. These values are implementation constants with boundary tests, not user-configurable API options.

The service does not need asynchronous jobs for this exercise. A transfer request finishes when the copy and destination publication finish. Status transitions are `running` to `publishing` to `completed`, and `running` or `publishing` to `failed`; `publishing` means every byte is staged and the destination is being replaced. Persist the initial record before I/O and persist the terminal state even when an expected connector error occurs. A `201` response always carries a `completed` record. An error response includes the transfer ID so the failed record can be inspected. Timestamps are UTC ISO 8601 date-times, and `updated_at` records the latest change. `bytes_copied` counts bytes passed to the staged destination and is saved about once per second while copying, so `GET /transfers?status=running` shows progress while the `POST` is still open; a nonzero value on failure does not mean the final destination was published. A record becomes `publishing` only after the sink has confirmed every byte, so a write failure the destination reports late is still phase `destination_write`. Count bytes rather than rows because a data-agnostic copy never parses records. Record the failure phase (`source_lookup`, `destination_lookup`, `source_open`, `destination_open`, `source_read`, `destination_write`, `publication`, or `interruption`) and the error code; the error message names the failing side and its connection. Because the owner lock guarantees one process, startup marks records left `running` or `publishing` as `failed` with phase `interruption` and code `TRANSFER_INTERRUPTED`, and the message states whether the destination may already contain the new file. Every state change is a compare-and-set on the state it requires: a record that has already reached `completed` or `failed` never changes again, and an attempt to change it fails with `TRANSFER_STATE_CONFLICT`. A database failure while writing a record is `TRANSFER_RECORD_FAILED`; if the file was published but completion could not be recorded, the response says so and the record stays `publishing` until the next startup marks it interrupted. At most four transfers copy at once; another request fails with `TRANSFER_CAPACITY_EXCEEDED` without creating a record, so worker threads stay available for other requests.

Every non-2xx response uses `{"error":{"code":"FILE_NOT_FOUND","message":"File not found","transfer_id":null,"details":null}}`, including unknown routes, unsupported methods, and unexpected server failures. `transfer_id` is set for a failed transfer request after its record is created. For `INVALID_REQUEST`, `details` lists every invalid field as `{"field": ..., "problem": ...}`, and the problem states the violated constraint. Each code maps to exactly one status; `databridge/errors.py` owns that mapping, and OpenAPI publishes the codes as an enum. Use these stable codes and statuses:

| HTTP status | Codes |
| --- | --- |
| 422 | `INVALID_REQUEST` for malformed request shape or field types |
| 400 | `INVALID_HOST_HEADER`, `INVALID_CONNECTION_SETTINGS`, `INVALID_FILENAME`, `SAME_FILE`, `UNSUPPORTED_PREVIEW_FORMAT`, `MALFORMED_FILE`, `PREVIEW_LIMIT_EXCEEDED` |
| 403 | `CROSS_ORIGIN_REJECTED` |
| 404 | `CONNECTION_NOT_FOUND`, `FILE_NOT_FOUND`, `TRANSFER_NOT_FOUND`, `ROUTE_NOT_FOUND` |
| 405 | `METHOD_NOT_ALLOWED` |
| 409 | `CONNECTION_EXISTS`, `DESTINATION_EXISTS`, `DESTINATION_NOT_WRITABLE`, `FILE_NOT_READABLE`, `PUBLISH_UNSUPPORTED`, `SOURCE_CHANGED` |
| 507 | `DESTINATION_FULL` |
| 502 | `SFTP_AUTH_FAILED`, `SFTP_HOST_KEY_REJECTED`, `SFTP_OPERATION_FAILED` |
| 503 | `SFTP_UNAVAILABLE`, `CONNECTION_ROOT_UNAVAILABLE`, `TRANSFER_CAPACITY_EXCEEDED` |
| 500 | `LOCAL_IO_ERROR`, `SOURCE_READ_FAILED`, `DESTINATION_WRITE_FAILED`, `TRANSFER_INTERNAL_ERROR`, `TRANSFER_STATE_CONFLICT`, `TRANSFER_RECORD_FAILED`, `INTERNAL_ERROR`; `TRANSFER_INTERRUPTED` appears only in records |

Avoid raw stack traces and secrets in error messages or logs. A remote authentication failure must not be reported as failure of the API caller's authentication. Keep the error mapper in the API boundary; below it, domain and connector code raises one exception type, `DataBridgeError`, that carries a typed `ErrorCode`, and never an HTTP status. Log one JSON event per HTTP request beside the SQLite database (default `state/databridge.requests.jsonl`), with mode 0600; rotate the log at 10 MiB and keep three owner-only backups. Include the route template, request ID, status, duration, relevant path/query parameters, and allowlisted connection or transfer fields. Never log passwords, keys, raw bodies, or arbitrary query parameters. Return the request ID in the `X-Request-ID` header of every response, including errors that no route handles.

**Browser boundary.** The API has no caller authentication, so web pages must not be able to use it. The service answers only requests whose `Host` header names an allowed local name (`127.0.0.1`, `localhost`, or `::1`; `DATABRIDGE_ALLOWED_HOSTS` overrides the list), which defeats DNS rebinding. A `POST`, `PUT`, `PATCH`, or `DELETE` request that carries `Sec-Fetch-Site: cross-site` or an `Origin` other than the service's own origin fails with `CROSS_ORIGIN_REJECTED`. JSON bodies require a JSON `Content-Type`, so a cross-site "simple" request cannot submit one. Clients such as curl send no `Origin` and are not affected.

## Design boundaries

1. **Connection store:** SQLite holds names, types, type-specific settings, and transfer records. Encrypt the SFTP password at the persistence boundary from the first implementation. Require a stable encryption key from the environment at startup, never store it with the database, and keep both the database and key material out of Git. Persist an encrypted key-check marker so a wrong key fails at startup, including when no SFTP connection has been created. The message names the database and the two corrections: the original key, or a move of the database to another name. Startup reads table names and metadata values as bytes, so a damaged value cannot raise a decode error. A SQLite error message that quotes a damaged name also cannot be decoded; startup reports it as a damaged file. A missing, empty, or non-ASCII marker means a damaged database; startup names the file and asks to move it aside. Store every secret field of a connection type (a `SecretStr` field) as one Fernet-encrypted JSON value, so a new connector type needs no schema change. Persist a schema version. Startup refuses a database from another version, a database without a version, a database without its `connections` or `transfers` table, a file that is not a SQLite database, and a corrupted file. The message names the file and quotes a stored version, so the message stays on one line. There are no automatic migrations. Create a missing state directory with mode 0700 and keep the database file at mode 0600. Close the owner-lock and database descriptors if permission hardening or lock release fails, so startup cannot leak a held lock. Reject a connection type that no model defines, both when writing and when reading a stored row. Return redacted connection views. Connection creation validates configuration shape; the healthcheck handles live connectivity.
2. **Connector contract:** A small protocol defines `list_files`, `check_access`, `read`, and `write`. `read` yields a byte source whose `read(size)` may return fewer bytes than requested; it returns the bytes the file held when it was opened, so bytes appended later are not read, and a file that becomes shorter while it is read fails with `SOURCE_CHANGED` instead of ending early. `read` takes an optional `limit` so a caller that needs a prefix (preview reads the budget plus one byte) does not make the connector fetch more. `write` yields a byte sink whose `write(data)` passes every byte on or raises, and whose `finish()` waits for every write result, makes the bytes durable where the backend can, and proves they are all stored; the transfer calls it before publication, and a connector finishes a sink that its caller did not. Every exception that leaves a connector or its streams is a `DataBridgeError` with a stable code. The local and SFTP implementations own path resolution, file opening, staging, and destination finalization. `write` publishes only when its context exits without an error; after any error the destination is absent or unchanged. Each active transfer owns its SFTP session and closes it on every outcome; no mutable SFTP client is shared across requests. A registry in `databridge/connectors/__init__.py` maps each connection type to its `open` and creation-time `prepare` functions (the local `prepare` creates and resolves the root); an unknown type fails closed, and a startup check proves every connection model has a connector. Reads accept regular files only, so a FIFO, directory, or device never blocks or streams without end.
3. **Transfer service:** Opens source and destination connectors, copies fixed-size byte chunks, checkpoints the byte count, and records each state through a `TransferLedger` protocol that the store implements. It does not inspect extensions or choose logic based on connector type. A same-file precheck compares stored connection names and validated filenames; different connection aliases to the same physical file are not identified, but staging prevents the early source truncation that check is meant to avoid. Stage a write under the reserved name `.databridge-{transfer_id}.part` in the destination root. Names that start with `.databridge-` in any letter case are reserved: API filenames may not use them, and listings omit them. A filename is at most 255 bytes in UTF-8, so every accepted name can be staged and published. The local connector writes the stage without buffering, calls `fsync`, verifies the staged size, keeps an overwritten destination's permission bits, and publishes with `rename` (overwrite) or a hard link (no overwrite); a filesystem without hard links fails with `PUBLISH_UNSUPPORTED` and suggests overwrite. The SFTP connector keeps up to 64 requests of 32 KiB in flight per file in both directions, as the OpenSSH client does, and checks the reply to every request: each write, `fsync@openssh.com` where the server supports it, and the close. It then verifies the staged size with a stat, keeps an overwritten destination's permission bits, and publishes with RENAME (no overwrite; OpenSSH never replaces an existing file, and a re-check covers servers whose RENAME does, except against a file created between the check and the rename) or `posix-rename@openssh.com` (overwrite; a server without that extension fails with `PUBLISH_UNSUPPORTED` and the destination is unchanged). If the connection is lost while the publish request is in flight, `SFTP_UNAVAILABLE` states that the destination may already contain the new file. SFTP cannot make the new directory entry durable, so that depends on the server's filesystem. A connector removes its stage only after a failure, including when the server created it but its OPEN reply failed, and a cleanup error is logged, not reported as a failed transfer. An SSH client teardown error after successful publication cannot turn the published transfer record into a failure. A handled write failure removes its stage so callers do not mistake a partial file for a completed transfer. After a process crash, an orphan stage may remain; the next startup marks the transfer failed, and the README gives a transfer-ID-based manual cleanup procedure. Automatic remote orphan cleanup is outside scope. An existing destination is refused by default; explicit overwrite is supported only with safe finalization on the target connector. The collision rule is checked before the copy and again at publish time, with the guarantee tested against the supplied SFTP server. If a remote server cannot finalize safely, report failure rather than success. Do not claim universal race-free behavior for untested SFTP servers.
4. **Preview service:** Reads through the connector contract and parses only supported formats. It keeps reading short reads until it holds 1 MiB plus one byte or the file ends. CSV uses its header and one tokenizer (`newline=""`), so only `\r` and `\n` end records, quoted newlines and Unicode separators stay inside values, a field may fill the whole budget, and blank lines are skipped. At the byte limit, a CSV record that may continue past the budget is never returned. JSON expects an array of objects; a row nested deeper than 32 levels is `PREVIEW_LIMIT_EXCEEDED`, checked for every row of a complete file and for each entry of a budget-cut prefix before the recursive decoder parses it, so deep input never exhausts a worker thread's stack (128 KiB under musl); past the byte budget, an entry the budget cut off is `PREVIEW_LIMIT_EXCEEDED` but a syntax error that more bytes could not fix (including an invalid token in the last bytes) is `MALFORMED_FILE`, and an unpaired surrogate escape, `NaN`/`Infinity`, a number out of floating-point range, or an integer with more digits than Python converts is `MALFORMED_FILE`. Limit returned rows (default 5, maximum 100, validated at the API) and bytes read; return a clear error when the preview cannot be produced within those limits. Empty/null values do not determine a type; compatible integers and floats widen to `float`, while incompatible values widen to `string`. Check booleans before numeric types. Inference uses ASCII grammars: integers are `[+-]?[0-9]+`, floats need ASCII digits and a finite value, and a date is exactly `YYYY-MM-DD` and a real calendar day. CSV text may infer numeric or boolean types; JSON numeric and boolean strings remain strings, while native JSON numbers and booleans retain their types. Return a clear error for unsupported or malformed input. Preview parsing never affects transfer bytes.
5. **API layer:** Validates requests, asks the connector registry to prepare a new connection (the local connector creates and resolves its directory), maps domain and connector failures to stable HTTP errors, and exposes typed response models and OpenAPI examples. A request middleware writes a single redacted JSON event after each response. Blocking SFTP operations use synchronous handlers.

Restrict API file names to one file at the configured root. Reject separators, `.`/`..`, and local symlink escapes; enumerate only regular files. Bound listing by entries scanned as well as files returned, and label a partial listing as truncated; ordering of a partial listing is unspecified. This keeps the exercise's file scope clear without designing a recursive virtual filesystem. For SFTP, verify server identity against a configured known-hosts source before authentication, so a password is never sent to an untrusted or changed host; document how to trust the local Docker server. A missing or unreadable known-hosts file fails closed with `SFTP_HOST_KEY_REJECTED` and names the file. A rejected key's message names the `[host]:port` entry that was looked up, the presented key's SHA-256 fingerprint, the known-hosts file, and the command that fixes it (`ssh-keyscan` for an unknown host, `ssh-keygen -R` first for a changed key). Set connection and I/O timeouts and close SSH/SFTP resources on every outcome; closing a session that already failed never replaces the original error. Healthcheck removes a probe if its OPEN reply fails after the server created the file.

**SFTP failure classes and server requirements.** A lost connection, a timeout, or a server status of "no connection" or "connection lost" is `SFTP_UNAVAILABLE`; a missing root is `CONNECTION_ROOT_UNAVAILABLE`; a missing file or a non-regular file is `FILE_NOT_FOUND`; permission denied is `FILE_NOT_READABLE` for reads and `DESTINATION_NOT_WRITABLE` for writes; any other refusal is `SFTP_OPERATION_FAILED`. A host name, username, password, or root that cannot be encoded for SSH is `INVALID_CONNECTION_SETTINGS`. The connector parses every reply with bounds: a reply larger than 256 KiB (the OpenSSH client's limit) or with a field that passes its end is `SFTP_OPERATION_FAILED`, and a per-session watchdog closes the connection when opening the SFTP session takes more than 10 seconds or sending one request or receiving its reply takes more than 30 seconds, even while the server sends one byte at a time or unrelated packets; that failure is `SFTP_UNAVAILABLE` and says the server did not respond in time. A supported server reports file sizes, answers an unknown extension with `SSH_FX_OP_UNSUPPORTED` as the SFTP draft requires, and supports `posix-rename@openssh.com` for overwrite. A READDIR entry without permission bits is classified with LSTAT, at most 64 lookups in flight. Only a missing or permission-denied LSTAT may omit that entry; a malformed or other failing reply fails the listing with `SFTP_OPERATION_FAILED`. Every raw entry, including `.`, `..`, and names that are not UTF-8, counts toward the scan cap, and a directory page without entries is a protocol error, so no server can hold a listing open. A read takes its size and type from FSTAT on the opened handle (after a STAT that keeps the server from opening a FIFO or directory), so a file replaced between the two is never copied truncated; a supported server answers FSTAT. fsync and close get 30 seconds plus the upload's size at 10 MiB/s, because both can take time in proportion to the upload. Listings omit names that are not valid UTF-8, because the API addresses files by text names.

## Verification and submission evidence

The live [requirement evidence map](verification.md) tracks R1–R14 as implementation and tests land. A planned row is not evidence of a passing requirement.

- Unit tests: deterministic schema inference, filename validation, transfer state transitions and failure cleanup, and shared connector behavior. Use a compact scenario table for both connectors rather than a separate test framework; keep connector-specific assertions where needed. Test empty files, exact/chunk-adjacent sizes, existing destinations, same-file copies, path and symlink escapes, truncated listings, and failure after a chunk has been written. Avoid tests that merely repeat the implementation.
- API tests: persistence across app restart, local-directory creation, response redaction, status/errors, redacted request events, and OpenAPI availability.
- Credential tests: inspect the stored row to confirm the password is absent in plaintext; restart with the same key and use the connection; reject an absent or wrong key at startup without disclosing secret material.
- Docker integration: follow the local trust bootstrap, prove an upload into the writable `data` directory from a fresh checkout, connect with valid and invalid credentials, list and preview via SFTP, transfer CSV and binary fixtures in both directions, and compare bytes. Exercise server-down behavior and service restart with an interrupted transfer record and reserved staging file; the record becomes failed and the staging name is absent from API listings.
- Large-file evidence: run a reproducible local-to-SFTP and SFTP-to-local benchmark at two sizes, targeting 16 MiB and 256 MiB when the environment permits. Compare SHA-256 hashes, report elapsed time, effective throughput, and peak process memory for each direction and size. Record host architecture, SFTP image architecture, Docker runtime/emulation if applicable, and disk/network conditions; these measurements describe the test environment, not a universal service limit. Where practical, separate connection, copy, and finalization timing so a slowdown can be attributed. Look for memory growth tied to file size or a disproportionate throughput drop. If a large run is unavailable, provide the largest successful measurement plus a bounded estimate based on chunk size, observed throughput, disk space, network/SFTP behavior, and synchronous request lifetime.
- Manual reviewer path: follow a fresh-checkout README exactly, including stable secret-key and known-hosts setup. After setup, run one documented smoke command against the actual Docker SFTP server, covering connection creation, preview, both transfer directions, status, and byte or hash comparison. Verify commands and examples against the final tree.
- Submission: working service; README with setup, API usage, decisions, cuts, and improvements; `ai-collaboration-summary.md` generated at the end from the brief's exact prompt and kept at or below 500 words; intentional Git commits.

## Source-specific setup notes and concerns

- The implementation layout is root-level `data/customers.csv`, `data/products.json`, and `docker-compose.yml`, with the supplied `instructions/` files retained as source material. Copy the supplied `customer.csv` under the plural target name; it has 15 customer records. Run Compose from the repository root so its relative `./sftp_data` mount resolves there.
- The root-level Compose file has a project-scoped named volume at `/etc/ssh` so generated host keys survive normal container recreation and `docker compose down`/`up`. It has no fixed project name: `make quickstart` writes a `COMPOSE_PROJECT_NAME` derived from the checkout path to `.env`, so two checkouts or worktrees never share a container or host keys. The host port (`DATABRIDGE_SFTP_PORT`, default 2222) and the container user's UID (`DATABRIDGE_SFTP_UID`) also come from `.env`. That UID is the host user's, so the bind mount is writable on Linux; on a root host it is the image's default 1001, because the fixture's sshd refuses every UID 0 login (`PermitRootLogin no`), and quickstart refuses a stored UID of 0 (`scripts/sftp_fixture_user.sh`). The local bootstrap creates `sftp_data` (a root host then gives it to the fixture UID), starts the container, and captures the key presented at `127.0.0.1` on that port into a gitignored known-hosts file with one scan; `localhost` is then trusted with the same keys (`scripts/trust_sftp_fixture.sh`), and a rerun adds nothing. Quickstart writes each `.env` value in single quotes and reads values back without running the file (`scripts/env_file.sh`); it refuses a double-quoted value, because Docker Compose and uv apply escape and interpolation rules inside double quotes that its reader does not, and it reads every value it needs before starting the fixture. The make targets that use the fixture load `.env`, and the tests, smoke check, and benchmark read the port and trust file through `scripts/sftp_fixture.py`. That helper has no defaults. When a value is missing, or the trust file does not exist, the check stops and names `make quickstart`. A guessed port could reach the fixture of another checkout. Integration tests verify write, read, rename, and delete inside remote root `data`. Capturing the presented key is trust-on-first-use for this local Docker test server only; runtime connections still reject unrecognized host keys. After `docker compose down -v` deletes the key volume, remove the old local `known_hosts` file before running `make quickstart` to trust the replacement container key. If a platform's bind mount denies writes, inspect permissions on `sftp_data`; matching the container UID to the host UID is one possible fix, not a prerequisite on every platform.
- Isolated preflight on 2026-09-24: the unmodified supplied Compose file worked on this macOS/Docker Desktop host (host UID 501, container user UID 1001), including SFTP upload, download, rename, and delete; both downloads matched the original SHA-256. The initially auto-created host directory was writable through this mount, so a UID mismatch alone does not prove failure here. Without a key volume, forced recreation changed both SSH host-key fingerprints and the old known-hosts entry correctly rejected the server. With a named volume at `/etc/ssh`, host keys stayed identical across forced recreation and `down`/`up`, and the previously trusted key still permitted SFTP operations. The Docker engine reported arm64 while `atmoz/sftp:alpine-3.7` is linux/amd64, so performance measurements on this host include emulation overhead. Repeat the write preflight on the reviewer's platform; this observation is not a cross-platform guarantee.
- Encryption needs a durable key setup and a restart test. Never generate an unpersisted key at each process start. Document that losing the key makes the stored SFTP credentials unusable; key rotation is outside this exercise.
- Transfer input is assumed stable for the duration of a copy; source snapshots, resumable transfers, automatic destination re-read checksums, and repeated-request deduplication are outside this exercise. Document this limit and measure file integrity in the integration and benchmark tests.
- This is a local, trusted development API with one shared connection and transfer namespace. Multiple callers can use it, but requests carry no user or tenant identity, so every caller has the same access. Bind the example server to localhost. Encryption at rest protects the stored password; it does not restrict what an API caller can do with a connection. A shared multi-tenant service would need TLS, because SFTP passwords travel in request bodies. It would also need authenticated tenant identity, tenant-scoped queries and authorization on every resource, isolated file roots and secrets, network access controls for user-supplied SFTP hosts, and tests that cross-tenant access is denied. One service instance per tenant is a simpler alternative if isolation is later required.
